# Phase 0 critical design review

Reviewed 2026-10-04. This is a design review, not evidence that ingestion, Spark, cloud resources, or performance tests have run. Requirements, architecture, roadmap and ADRs were inspected before runtime implementation. Contract inspection and executable schema validation are recorded below when completed.

## Gate decision

**Pass for the local foundation only.** Machine-readable schemas, six product contracts, 24 event examples and their invalid empty-payload counterparts passed the executed design gate. The resolutions below define implementation obligations. Subsequent milestones require their own executed acceptance tests. AWS publication, deployment, SLA compliance, Redshift performance and managed-service failure behavior remain **not accepted / unmeasured**.

The central design is sound for a bounded, single-writer portfolio workload: retained raw evidence, one authoritative batch path, event-time business reconstruction, immutable snapshots and an explicit publication pointer. Calling it production-style does not establish production readiness.

## Findings and required resolutions

| ID / severity | Finding and consequence | Accepted resolution / implementation acceptance |
| --- | --- | --- |
| P0-01 / high | Concatenated Firehose bodies do not preserve record boundaries. Delimiter-only framing loses arbitrary malformed bodies containing newlines. | AWS producers send a valid JSON wire envelope containing `record_id`, a transport version and base64-encoded original body; Firehose inserts a delimiter between envelopes. Preserve malformed business bytes and quarantine malformed transport separately. Local JSONL tests cover malformed individual lines; arbitrary binary/newline payload coverage belongs to the wire-envelope tests. Neither mode claims the other's transport behavior. |
| P0-02 / high | Architecture and ADRs initially described different Bronze contents. Excluding malformed records makes rejected-record reconciliation depend on an unrelated side output. | Bronze retains original body/provenance and parse disposition, including invalid business records. Silver accepts only normalized contract-valid records. Immutable raw remains the ultimate replay source. Early Lambda quarantine is a signal copy; batch disposition is authoritative and the two are never unioned as input. |
| P0-03 / high | A producer-provided `ingestion_timestamp` can predate actual availability. Replacing arrival with replay time breaks reproducibility; using an event's own timestamp leaks unavailable events into features. Opaque Firehose delivery does not preserve Kinesis arrival metadata. | Local fixtures carry deterministic observation times. Authoritative AWS batch availability uses persisted original S3 object `LastModified` as a conservative observation; Lambda independently uses Kinesis arrival for its early signals. Persist original observations with raw provenance and retain them through copies/replay. Distinguish occurrence, stream arrival, object delivery and processing clocks; do not label object-to-publication latency as end-to-end latency. Feature eligibility requires both occurrence and original batch observation at or before cutoff. Arrival metadata is excluded from business identity comparison. |
| P0-04 / high | Completeness language both credited rejected events and excluded them. That could make a product with every record rejected report complete. | Source completeness is accepted distinct expected IDs divided by independently declared distinct expected IDs within the defined scope/deadline. Product contracts additionally measure transformation coverage against keys in the committed effective Silver population; this can pass while source completeness fails and cannot substitute for the source SLO. Accepted plus durably rejected is reconciliation coverage, a third metric. With no authoritative control total, source completeness is `unknown`. Denominator zero is explicitly `not_applicable`, not an invented 100%. Record expected, accepted, rejected, missing and conflicting counts separately. |
| P0-05 / high | Deduplication can accidentally make conflicting payload selection depend on filesystem order or erase correction history. | Same immutable event ID plus same canonical business content is a duplicate; differing business content is an identity conflict that blocks affected publication. A correction is a new event ID with an explicit target, not mutation of an old record. Preserve immutable history. Validate correction references, cycles and competing replacements deterministically. Resolve effective events at the requested availability cutoff, so a later correction cannot rewrite what was knowable earlier. Reconstruct the corrected fact at the target's business position; a higher correction version must not append the old lifecycle transition. A new correction cannot itself erase conflicting raw variants: conflict recovery requires an explicit audited input-disposition decision, and remains manual/blocked until that workflow exists. |
| P0-06 / high | A committed product plus failed feature/catalog update could expose mutually inconsistent state. Object-store rename is not an atomic commit. | Validate all required products and features before switching the single local committed head. Readers resolve every artifact from one immutable manifest; filesystem globs and independent latest-product pointers are prohibited. Fault injection before and after head publication must prove old-or-new visibility and safe retry. Cloud jobs write run prefixes; single-writer scheduling is an operational constraint, and CAS/coordinator plus catalog publication/recovery is required before cloud acceptance. No cloud coordinator is claimed as implemented. |
| P0-07 / high | A date-bounded replay can remove unaffected records or compute a current shipment from incomplete history. Late corrections also affect downstream rolling windows. | Initial local snapshots read full retained history. A bounded backfill publishes to a separate range namespace and cannot replace the current global head. Use an explicit output interval and maximum span, but include complete histories for affected entities; the first implementation may scan full history to obtain them. Recompute dependent aggregate windows and feature lookback/forward impact. Test dates on either side of midnight and unaffected-entity preservation. |
| P0-08 / medium | Event-time tie breaking can invent valid order from an impossible or ambiguous lifecycle. Missing predecessors may merely be late. | Separate incomplete/pending history from invalid transitions. Use contracted causal evidence where available and a documented deterministic tie policy for reproducibility; stable sorting alone is not proof of causality. Tests must demonstrate a late predecessor repairing pending state and an impossible transition remaining invalid. |
| P0-09 / medium | Design SLO percentages are easy to confuse with achieved SLA evidence. Attempt counts also inflate duplicate-heavy throughput or rejection rates. | Label all target percentages as design targets. Report attempts and unique outcomes separately, define eligible population/window/deadline, and preserve unknown/non-applicable states. Measured local durations require command, environment, input scale, clock and result artifacts. Synthetic scheduled arrival is not observed cloud latency. Cloud SLO compliance remains open until deployed reconciliation exists. |
| P0-10 / medium | Small local workloads cannot justify Redshift distribution keys, compression or claimed performance gains. | Keep the initial physical design a hypothesis. Retain reproducible scale generation, query text, EXPLAIN output, cluster/workgroup settings, result checks and actual latency captures before recommending changes. Do not substitute local SQL timings for Redshift results. |

## Required milestone proof

The first local runtime gate must exercise contract versions, deterministic source generation, preserved malformed input and source-addressed quarantine. The lakehouse gate must add duplicates across batches, conflicting IDs, retry after partial staging, commit visibility, replay equivalence, bounded output scope, late-history repair and correction propagation. The product/feature gate must add referential integrity, independent completeness control totals and point-in-time leakage tests.

Failure recovery measurements must describe the injected failure and recovery boundary. A rerun completing successfully is not enough unless committed data matches the clean reference and stale staging cannot become visible. These are future acceptance obligations at review time, not executed results.
